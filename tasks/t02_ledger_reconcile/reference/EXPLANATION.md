# Root cause and fix

## Root cause

For every transaction the baseline scans **all** ledger entries (`O(n*m)` comparisons),
then does two more list-based lookups:

- `entry.id in matched_entry_ids` where `matched_entry_ids` is a `list`: an `O(k)` scan per
  candidate.
- `unmatched_entries = [e for e in entries if e.id not in matched_entry_ids]`: another
  `O(m*k)` pass at the end.

Per-candidate tuples are also built and sorted for every transaction even though only the
minimum is needed. At 100x the original input the dominant term grows 10,000x.

## Fix

1. Bucket entries by `(account, amount)`: a transaction can only ever match inside its
   bucket, so everything else is never touched.
2. Keep each bucket sorted by booking date (as an ordinal) and `bisect` to the start of the
   tolerance window. Only entries inside the window are examined.
3. Select the best candidate with a single-pass minimum over the key
   `(not reference_hit, |day diff|, input position)`, the same ordering as the old sort.
4. Pop the matched entry out of its bucket (`O(bucket)` list deletion, tiny and done in C)
   so recurring-fee buckets do not accumulate dead entries, and track matched positions in
   a `set` for the final unmatched list.

Complexity is `O(m log m)` to build plus `O(n * (log b + w))` to match, where `b` is the
bucket size and `w` the number of entries inside one tolerance window.

## Things a careless optimization gets wrong

- Dropping or reordering the reference-hit preference (candidate `drops_reference_rule`).
- Using `.lower()` instead of `.casefold()` (differs for "ß" vs "SS").
- Using the entry *id* instead of its position to break ties.
- Replacing only the `list` with a `set` (candidate `set_for_matched_ids`): faster, still
  quadratic.

## Residual risk

If a single bucket holds very many entries inside one tolerance window (e.g. 100k
identical fees on one day), matching degrades toward `O(n * w)`. A heap per
`(account, amount, day)` would fix that at the cost of more code; it is not warranted by
the data described in the problem.

## Measurement

See `results/t02_ledger_reconcile_bench.md` (generated by `codeforge bench
t02_ledger_reconcile`). The tests do **not** use wall-clock time as the primary signal:
`tests/test_scaling.py` counts executed source lines with `sys.monitoring` and checks the
growth ratio when input is quadrupled, which is deterministic on any machine.
`hidden_tests/test_budget.py` is a loose wall-clock backstop that is run in a child
process with a hard kill.
